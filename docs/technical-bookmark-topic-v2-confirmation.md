# Technical bookmark topic v2 confirmation corpus (candidate)

This records the pre-split combined router (before 2026-09-25).

Status: confirmation data authored and frozen on 2026-09-21 before inference.
The lead records measured results below. The corpus alone provides no approval.

## Intended scope

`technical-bookmark-topic-v2` is the same narrow, low-risk classification profile as
v1: it groups a bookmark into one of four subject labels. It is topic grouping only.
It is never keep/drop, safety, merge approval, plan classification, or execution
routing. Those decisions stay on Jev and are out of scope.

This corpus is the independent confirmation set for the frozen v2 candidate
(`checkpoint` `aac6fef/laya-typed-decisions-mlx`, `revision`
`28416e78cb26a239a4eabaa2e084904ec5e6cacb`). The lead froze the typed candidate before
this corpus was authored; the author of this corpus did not choose, revise, or
re-freeze it.

## Frozen definition

The exact frozen question object lives in `config/technical-bookmark-topic-v2.json`,
under `questions`. Every row in the corpus embeds that object verbatim, including
option order:

```json
{
  "topic": {
    "type": "choice",
    "instructions": "Choose the main subject of this bookmark. Judge the primary subject of the title and description, not incidental words that appear in them.",
    "criteria": {
      "software_development": "programming, databases, software testing, deployment or software security",
      "machine_learning": "model training, inference or machine-learning research",
      "computer_hardware": "physical components, processors, memory, electronics or peripherals",
      "other": "content outside those subjects"
    }
  }
}
```

The rows were generated by copying this object from the config file, not retyped, so
the serialized questions match byte for byte and the harness fingerprint is preserved.
Changing any word of the instructions or reordering the criteria invalidates the
corpus.

## Corpus

One file, `data/technical-bookmark-topic-v2-confirmation.jsonl`:

| File | Split | Cases | Per label |
| --- | --- | --- | --- |
| `data/technical-bookmark-topic-v2-confirmation.jsonl` | `holdout` | 400 | 100 |

Per-label counts: `software_development` 100, `machine_learning` 100,
`computer_hardware` 100, `other` 100. Every row is `origin: synthetic` and
`split: holdout`. IDs use the new `tbt-v2-confirm-` prefix and run
`tbt-v2-confirm-<label>-01` through `-100`.

Cases with incidental cross-category wording, where the stated primary subject is
defensible against the incidental term: `software_development` 24,
`machine_learning` 27, `computer_hardware` 22, `other` 36. Each such row's
`label_reason` names the incidental term; some states also state a primary-topic contrast. This can make classification easier.

### Row schema

Each JSONL row follows the harness contract used by `tools/laya_compare.py`
(`load_cases`, `validate_cases`, `extract`):

- `id` — unique across the file (prefix `tbt-v2-confirm-`).
- `group` — equals the expected label, so the harness groups accuracy by label.
- `split` — `holdout`.
- `origin` — `synthetic`.
- `state` — `{ "title": ..., "description": ... }`, a short realistic bookmark title
  plus a description. All serialized states are below `maxStateChars` (2000).
- `questions` — the exact frozen question object above (one `choice` question, id
  `topic`), copied from the config.
- `expected` — `{ "topic": "<label>" }`, the question-id map the harness requires,
  never a scalar.
- `label_source` — `agent-authored synthetic; Lena head; not human-labeled`.
- `label_reason` — a concise reason for the label.

## Authoring method

Each label was assigned by reading the title and description against the frozen
criteria, not by matching keywords. Labels were written before the row was
serialized; the frozen question object was injected from the config at serialization
time. The author read `data/technical-bookmark-topic-dev.jsonl` and
`data/technical-bookmark-topic-holdout.jsonl` only to avoid reusing cases or close
paraphrases. Exact input duplicates were absent across the three corpora. Related
subjects still occur across splits; distinct wording does not establish statistical
independence. Subjects and primary-topic contrasts were varied deliberately, but
keyword cues remain possible.

Boundary conventions applied consistently:

- Software implementation, testing, deployment and software security are
  `software_development`, even when the tool runs on specific hardware.
- Model training, inference and ML research are `machine_learning`, including data
  preparation, evaluation and serving of models.
- Physical components, processors, memory, electronics and peripherals are
  `computer_hardware`, including embedded boards, test instruments and camera
  hardware.
- Everything outside those subjects is `other`.

## Label ambiguity and limitations

- The labels are authored by an agent (the Lena head) from a rubric, not by a human
  annotator, and the cases are synthetic. They are not real user bookmarks and not
  representative browsing traffic. No private browsing history, repository diffs, or
  external data were used.
- Each label reflects one authoring pass over a short title and description.
  Ambiguous edges — a firmware post, a robotics post, a statistics post, a
  hardware-adjacent coding post — were resolved by the stated conventions; a
  different annotator could disagree on some rows.
- Expected label fields and label reasons are excluded from `state`. Some states
  explicitly contrast primary and incidental subjects, which can cue the label.
- Generated data does not establish production representativeness. A passing or
  failing result on this corpus says nothing about real bookmark traffic, and any
  accuracy, latency or threshold claim must come from the lead's frozen qualification
  run, not from this file.
- `sampleCount` in any future evidence file is a count of cases, not a claim of
  statistical power.

## Measured confirmation result

The lead ran the frozen candidate on 2026-09-21, then evaluated the saved predictions.
The model, question text, option order and selected-probability threshold (0.4) did
not change. All frozen input hashes still match. There were 400 local predictions
and 400 successful Jev requests, with no retries or schema errors.

| Measurement | Result |
| --- | --- |
| Jev accuracy, all 400 | 94.5% (378/400) |
| Typed Laya accuracy, all 400 | 74.75% (299/400) |
| Proposed local/Jev combination | 92.0% (368/400) |
| Accepted local coverage | 54.5% (218/400) |
| Accepted local accuracy | 88.53% (193/218); required 95% |
| Accepted local minus Jev accuracy, paired 95% interval | -10.09 to +0.46 percentage points |
| Accepted local/Jev median warm latency ratio | 0.02487 |

Selected counts were 71 software, 36 machine learning, 50 hardware and 61 other.
All count gates passed. The absolute accuracy gate, overall comparison gate, and
three category comparison gates failed. The large latency advantage does not
compensate for the accuracy failure. Timings exclude model loading and downloading;
local inference and a hosted API have different deployment costs.

The qualification result is **FAILED**. The registry records v2 with `enabled: false`.
No threshold was changed after this result. Jev remains the answer provider, while
configured Laya shadow comparisons remain available. This result does not establish
a general ranking beyond this authored synthetic corpus.
